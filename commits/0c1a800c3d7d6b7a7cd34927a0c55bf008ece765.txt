ticket 200: the group checks bound the interpreter's drop by what the C stood in for
Four slow checks still asserted that `next` and `legacy` *interpret the same
number of instructions*. That was the right statement while `legacy` was the
generated translation and the port's C only took over a translated case: the
interpreter's count stood still because nothing it ran changed. With one
execution path it is the wrong statement -- the interpreter is what the C
replaces -- so the checks now assert the drop and bound it the way the group's
shape requires:

* `tests/test_units.sh`, `tests/test_structures.sh` and `tests/test_orders.sh`
  are chunked groups (a dispatch stands in for several guest instructions), so
  the bound is the sum of the rows' `guest_instructions`, not the dispatch count
  -- the units group's 450 472 orders dispatches stand in for 7 313 251 guest
  instructions, and the old `calls` bound would fail a correct run.
* `tests/test_unit_lifecycle.sh` compares two selections against each other, and
  `tests/test_map_renderer.sh` pins the undecoded copy loop: both now read the
  drop the same way, and both print the interpreter's share instead of asserting
  it is unchanged.

`port/next/order_actions.c` and `_2.c` are regenerated by
`scripts/transpile_next.py --check`'s generator: the MOVEQ fix made the
generated lines longer, so the parts' 240 KiB split moved 37 cases from the first
file to the second. Same cases, same behaviour; the split is by size by design.
