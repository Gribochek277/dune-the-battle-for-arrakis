the group attack leaves a harvester's target alone
The playtest's abort: `md68k: address error at $004021 (pc $0053DE)` with
`pointer: gesture=order` just before it. The faulting record is a harvester
(type $10) whose `+$54` is still 5, the harvest order it was already running,
and whose `+$5A` holds a unit handle -- the fault is `$0053BA`'s widget
reading `+$5A` as a sprite record, and the address is the handle.

The cartridge cannot reach that state: `SetUnitTarget`'s head (`$01D2D4`,
`cmpi.b #$10`) refuses a harvester before its tail writes `+$5A`. The port's
copy for the rest of a box selection (`next/mission_orders.c`,
`set_unit_target`) transcribed the tail only, so a group attack wrote the
handle into a harvester -- the order was busy, so `SetUnitOrder` queued it in
`+$55` and `+$54` stayed 5, which is exactly the harvest widget's path.

The fix is the guest's head: the target is not written for a harvester. The
order itself still is, because the guest's `SetUnitOrder` does not refuse it.

`tests/test_orders.c`'s "an attack leaves a free harvester's target alone"
drives a tank and a free harvester through a group attack: red before the fix
(`+$5A = 0x4028`), green after, with the guest's own `SetUnitTarget` run on the
same record as the control.
