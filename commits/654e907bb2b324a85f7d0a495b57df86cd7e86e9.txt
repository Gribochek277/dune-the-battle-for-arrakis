ticket 93: the port's row opens the front end's list, and the way back clears it
app/mapping_screen.c inverts the run's map into rows -- a map is control-to-function,
which is how a file is written, but a player holding a pad asks function-to-control,
which is how a screen has to be laid out. The vocabulary is the binding file's own
(mda_function_name, mdp_gamepad_control_name), not a friendlier set invented here: a
second set of names would be a second thing to keep in step with the file format, and
a player who has read gamepad-map.ini should find words they already know.

next/settings_screen.c gains one pointer -- the list that is up -- and three questions
asked of it, so both lists are drawn by the same code, wrapped by the same code and
marked by the same code. Two things it found by being wired up:

* The input block counted the settings rows to decide where the cursor wraps, so the
  ten-row mapping list stopped after its second row and the rest was unreachable. The
  same class of bug ticket 101 names from the other direction -- a clamp borrowed from
  a list that is not the one on screen -- and it is now the list that is up.
* Returning from ten rows to two left eight rows of the front end's words in the plane:
  'pad_mode  back' sitting under 'BACK TO TITLE' reads as a third option that does not
  exist. The screen owns those cells while it is up, so it clears the ones it is not
  using, and the test says so by name.
