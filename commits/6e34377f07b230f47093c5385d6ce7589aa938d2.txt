ticket 90: the title screen is the port's C, proved, gated and documented
The slice ticket 84 made possible and ticket 89 named: RunTitleScreen $00CFCC
-- the screen with START GAME / OPTIONS / LEVEL, the one the owner plays on and
the one PORT SETTINGS has to be a row on -- runs as the port's own C in `next`.

Proof on analysis/recordings/house-selection.pad, --engine legacy against
--engine next --replace RunTitleScreen:

  2700 frames, 8078 calls: instructions 31859412, cycles 347408292, picture
  230723 B / 71680 px, work RAM 65536 B (sha256 06bfd63d...), audio 1997366
  samples, YM2612 timeline 6023353 B, 17197 control + 6685 data VDP writes and
  1288 DMAs, the Z80's whole state -- identical, with the translation running
  exactly 8078 fewer instructions over 8078 calls, one per call.
  2400 frames with three DOWN presses, 14928 calls: identical again.

That recording carries the screen, the dispatch and the handoff because the
routine has two entry paths and all of them appear in it: entries 1..2007 are
the intro, which the port does not own and hands back to the guest instruction
by instruction; 2008 is the first frame the title screen itself draws; the
press at 2203 is START on the first row, which leaves with the result 0.

The row list is data, and that is measured, not claimed. A second binary with
one entry added at $B8 -- the slot ticket 91 measured as the socket the removed
tutorial row left, and the slot ticket 85's PORT SETTINGS will use -- is byte
identical to legacy with a recording that never walks to it, and 12693 of 71680
pixels (16.53 %) away from the guest's own cursor with the walk. No drawing code
and no navigation code changed between the two builds. legacy keeps the guest's
three-row range: it runs the guest's own selector, which cannot reach $B8.
