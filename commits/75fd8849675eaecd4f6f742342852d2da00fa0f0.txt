platform: a failed window attempt stops ending every SDL subsystem (ticket 10)
Two checks were red on `main` for one cause, and it was not the pad:
`port: the gamepad drives the machine's pads` saw an empty timeline and
`port: the whole binding flow...` never moved its menus, because its whole press
schedule is the same scripted pad.

Measured in the run: the pad is attached and reported (`gamepad "Virtual
Controller" on port 1`, no missing control), but at the first scripted press
`SDL_WasInit(SDL_INIT_JOYSTICK)` and `SDL_WasInit(SDL_INIT_GAMECONTROLLER)` are
**0** -- the subsystem `mdp_gamepad_open()` started before the window is gone --
so `SDL_JoystickSetVirtualButton` is a no-op and the controller reads zeros.
`--record-input` stays empty and `PadHeld` `$FFFFE41B` stays 0, while the same
run's keyboard path is recorded; SDL itself is fine (a standalone probe reads the
same virtual pad with the same default mapping).

The taker is the presenter's fallback (D153). `--presenter gpu` tries the Vulkan
window first; a host that cannot give one -- SDL's dummy driver, a VM, a build
without Vulkan -- fails the attempt, and the failure path called
`mdp_window_close()`, whose last line is `SDL_Quit()`: every subsystem. The
fallback surface window then works and the run plays with a pad whose subsystem
is dead, which the backend cannot know (`pad->started` is still 1).

`mdp_window_abandon()` is that attempt's own undo -- the objects, the cursor and
itself -- next to `mdp_window_close()`, which stays the process's teardown and
keeps `SDL_Quit()` (the Vulkan loader is unloaded there, in the order
`mda_play_presenter_free()` already uses). The window's own open failures use it,
and so do the presenter's two Vulkan fallbacks (no loader, no device/surface):
one window that was never there ends nothing that another module started.

green (bind, swap, save, reload, the game's own screens intact), and the checks
that drive the same fallback still green: `tests/test_input_map.py`,
