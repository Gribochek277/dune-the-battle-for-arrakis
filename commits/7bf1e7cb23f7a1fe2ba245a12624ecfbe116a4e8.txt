The port's screens say keys, and a locale file says the words
Ticket 122. Every string the port's own screens show is a key now -- the
title menu's rows, the settings screen's title, rows and capture prompt, the
options screen's row list, the house selection's rows and the front end's
mapping sentences -- and `--locale LANG` reads the [LANG] section of
`locale.ini` beside the binary. English is the table the code ships
(next/words.c), so a run without the flag reads no file and says exactly what
it said before; the shipped `port/locale.ini` is that same English written out,
and port/tests/test_locale.c compares the two key for key, so the file and the
code cannot drift into two Englishes.

The format is the binding file's (D40, docs/locale.md is its page): one section
per language, one `key = value` line per word, values verbatim after trimming,
and every bad line a load error naming its number -- an unknown key, a key set
twice in one language, a malformed line, a second section with the same tag, a
line before the first section, a too-long line or value, a `%s` count that does
not match its key, a language the file does not have, and a file that is not
there (the binding file's absence falls back to the built-in map; a language's
does not exist until the file names it). A *missing word* is not an error: it
reads in the port's English and is reported once at load, because a translation
in progress has to render.

The row lists became the shape the mouse and the wide layout are waiting for:
every row carries an **id** its translation does not change, a **text key**, a
**band** (its rectangle in the screen's text plane, in cells) and its **action**.
The bands are measured, not invented -- the title menu's at $D4A0 + $100 (plane
row 41, column 16), the settings rows at $C400 + $100 (column 8), the options
screen's labels at plane B $A000 column 4 on rows 5, 7, 9 ... (read out of the
port's own VDP dump of that screen), the houses' where the strip stands over
each banner (data_02529A, 10 x 2 cells) -- and nothing draws from them, which is
why the picture did not move. port/tests/test_row_lists.c holds the properties:
unique dotted ids, keys that read as words, bands inside the plane, no two rows
of one list overlapping, every action set.

The evidence is the picture, not the code:

* `--locale en` with the shipped file reproduces the port's settings screen's
  VDP dump **byte for byte** (tests/test_locale.sh);
* a `[test]` section changes "PORT SETTINGS" to "TEST LANGUAGE", "GAMEPAD
  MAPPING" to "PAD MAP" and "BACK TO TITLE" to "BACK TO THE START", and the two
  dumps differ in 30 bytes, all of them inside the three bands the words occupy;
* the title screen's own row follows the same file ($D7A0 reads "PAD SETTINGS"),
  and so does the front end's mapping list on the settings screen ("PAD MAPPING",
  "HIT A %s TO REBIND"), while the binding file's own names still read `PAD_UP`
  and `DPAD_UP` -- those are spellings a file has to parse back, not prose;
* the same file, run through the playable window, draws "WINDOW WORDS" and "PAD
  WORDS" on the same screen;
* every bad file is refused with its line, and a word a language lacks is named
  once and reads in English.
