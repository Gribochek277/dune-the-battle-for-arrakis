The player's word after playing with ticket 162's pair: left is the pad's A
and right is its B. A left release in place is the A -- the select at the
pointer's own target with nothing selected, the guest's own command (mark the
primary and re-post it) with a set standing; a left press that drags is still
the selection box and its release is never a button. A right press is the B,
the mission's own cancel, wherever the hand is. Ticket 162's contextual rule
is deleted, not left behind a flag: `release_a()` in next/mission_mouse.c is
one function and it always answers the same button.

Where it lives:
  * app/input_map.c: the left button carries POINTER_CLICK (the gesture) and
    POINTER_ORDER (the A its release delivers); the right button carries
    POINTER_BACK, the same function the menus read as their way back; the
    middle stays POINTER_DRAG. The function names are unchanged -- the map
    decides the button.
  * next/mission_mouse.c: step 3 is the right button's B (read when no select
    gesture is in progress, so a cancel cannot be undone by the box's own
    release); step 4 is the order as a press of its own, only for a map that
    binds POINTER_ORDER to a control which is not the select's (the shipped
    map binds both to the left, where the release is the A, so a press can
    never command before it knows it is not a drag); step 6's release is the
    A. The panels' leave is the back edge (or a clear), never the order: the
    left button must keep choosing.
  * app/run_play.c: the screens' back edge is the back function, not
    `back || order`, because the left button carries the order too and a left
    click must keep activating a row. The startup line names the new pair.
  * The B is injected at the same two instructions the A is
    (`$003118`/`$003AD0`), so `$00364A` posts `$42`; it never becomes a pad
    byte.
