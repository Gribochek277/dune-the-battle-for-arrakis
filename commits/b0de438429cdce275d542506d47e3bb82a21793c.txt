ticket 207: the structure band and the mission's run are the port's C
Ticket 189 took the structure subsystem's rules (seven rows) and ticket 206 the
interface below the map; the band after both -- 84 routines of `$00749E-$00CB5E`
that no group owned -- is this ticket. It is two subsystems' worth of code, and
the split's boundaries say where each half belongs:

  group `structures`, paired, 65 rows (58 new, 72 routines), zero delegations
  group `mission-run`, paired, 26 rows, zero delegations

The band extends `structures` because it is the same subsystem: the pass's
per-record handlers (`sub_00749E`-`sub_007E14`, the table at `$FFFFD30C`'s
arms), the production half with the session's unit command handler
`seg_code_0089AA`, the placement `PlaceStructureOnMap` $008DCA with its scan
`sub_009342`, the footprint test `TestStructurePlacement` $0094F6, every command
(`ApplyStructureCommand` $009E10, `CancelStructureBuild` $00A35C and the seven
helpers between them), and the map's own arithmetic and drawing (`CellDistance`
$00AD4A, `JitterPosition` $00AE62, `DrawPaletteText` $00AFC2, the HUD pass
`sub_00B0FA`, `RefreshMapSprite` $00B378). A second group would give one
subsystem two stages (D91). The mission's run is its own: the three end screens,
the campaign end's line walker and slides, `RunMissionUpdate` $00C172 with its
four-way dispatch, `CreateMissionForce` $00C718, `StartNewMission` $00CA0A,
`InitOrderEntry` $00CB3C and the helpers between them.

Two dispatch shapes in one group. Ticket 189's seven parts are chunks (D103);
the band and the run are stepwise, one guest instruction per dispatch, because
the six fixtures the band inherits were recorded that way and a chunked dispatch
answers a state the fixture never entered (D116's measurement). The manifest in
scripts/transcribe_group.py carries the shape on the part, not the group, and
the gate asserts the accounting either way: the machine's steps fall by exactly
`guest_instructions - calls`, `translated` falls by the rows' guest instructions
minus the dispatches the C hands to the interpreter (the jump tables' `dc.w`
words), and `interpreted` is the same in both arrangements.

The split had lost the band's tails, and the port's own run proved it. With the
band's C on, the mission recording faults at `$008782`: the instruction before
it falls through into a `seg_data_*` blob. Seven regions are code -- the tails of
`sub_008222`, `sub_00874A`, `sub_0087A4`, `sub_0088C0`, `sub_00895E`,
`sub_00B3B2` and `sub_00B4C0` -- and disassembly/code-candidates.txt carries the
evidence for each (a fall-through, a branch target, or an address the run
executed). Re-splitting merges seven segments into two; the old blobs were the
routines' tails. The image stays the dump plus the header's 42 bytes and the
other groups' transcriptions and fixtures do not move (tests/test_oracle.sh
replays them all).

A third entry kind for a row the guest enters with a branch. `$0087A4` and
`$00B412` are rows the split names as routines, but the guest reaches them by a
`bne`/`beq` and a fall-through from inside the routine that contains them, and
the code between the call and the label uses the stack as scratch. The
mechanism's call-shaped-frame check is right to refuse that state, so they carry
`NEXT_ENTRY_JUMP`: the frame belongs to the enclosing caller and the only check
is the 68000's even stack pointer. port/tests/test_frame_clock.c proves the kind
accepts the state the call kind still refuses. The windowed run then found the
same shape in ticket 206's unit-spawn body `sub_005FA0`, which a saved mission
state reaches with the AI's reinforcement order -- the played build aborted on
it, and the row now carries the same kind (its fragment says why).
