212: UpdateMapViewport answers $0029AE, the call into its span's middle
A player's `dune-port --engine next` session aborted with

  replacement: UpdateMapViewport at $00297C: the replacement reported no cost;
    the guest's routine always costs 68000 cycles, so 0 means it did not run
  md68k: replacement state at $00297C (pc $0029AE, sr $2008, info $0)

after a mouse session with a three-unit move order, a refused order, a cancel,
clicks and a selection box.

$0029AE is what the address is: `sub_0029AE`, the draw script's end -- the arm
`UpdateMapViewport`'s own `beq.s $0029AE` at $00299A takes when the script's next
source long is zero -- and it is a `bsr` target too. `RefreshMapFully` $002B82,
the map teardown `$010E86` runs when a mission screen is left with a map up,
reaches it with `bsr.w sub_0029AE` at $002B88, which pushes $002B8C and leaves
the pc inside the row's own span. The span ($00297C-$002A95) covers the address;
the dispatch had no case for it, so it returned 0 and the mechanism read the 0
as "the C did not run". It is not a branch target the span should not own and
not a delegate's business: it is the same state machine one address further in,
entered with a call's frame, and the `rts` at $002A94 returns through it to
$002B8C.

The row now answers it as `resume == 2`, the epilogue and the repaint window the
`beq` at $00299A would have run -- one code path, two ways in, no second body.

The reproduction is in port/tests/test_mission_map_view.c (fast tier, `make -C
port test`): the mission map's state at the teardown -- the overlay's node, the
reveal still running with a unit on the row -- entered at $0029AE with $002B8C
on the stack. Before the fix it printed the crash's own sentence and failed 16
checks; after it the guest's own code and the row agree on every register, the
flags, the 64 KiB of work RAM, the VDP's write counters and the 13 360 cycles.

The rest of the span is swept, which is what the ticket asked for. The listing's
call graph says the span has exactly six addresses the machine can hand the row
to: the entry, $0029AE, and the returns of `jsr (GetUnitByIndex).w` at $002A54,
`jsr (GetStructureByIndex).w` at $002A5A, `bsr.w PackMapRow` at $002A84 and
`bsr.w UploadMapRow` at $002A88 ($002A58, $002A5E, $002A88, $002A8C). The one
call out that is not a resume is $0029AA's `jmp (QueueDmaTransfer).w` -- a tail
call pushes nothing -- and so are the three conditional branches out of the
span. Each of the six is now a fixture case ("the span answers every start"):
its own constructed state, the first step checked to be the row's dispatch the
mechanism charged for, then the guest against the C. Removing one case from the
dispatch makes that fixture fail with the same "no cost" sentence, so the check
is not decorative. tests/test_mission_map_view.sh derives the same six from the
committed listing (a new call into the span fails the gate until it is answered
and listed) and, from the route's own `--flag-inventory` record, requires that
the row delegated nothing and answered every address the dispatch offered it --
$00297C on this route, the other five named as the fixtures' because no route
